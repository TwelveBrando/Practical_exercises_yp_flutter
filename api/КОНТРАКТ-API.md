# API агентства Alibi для практической работы 4

Базовый адрес задаётся в Flutter через `--dart-define=API_BASE_URL=http://localhost:8080/api`. Формат обмена — JSON UTF-8, идентификаторы — положительные целые числа, даты — ISO 8601. Для запросов с телом требуется `Content-Type: application/json`.

Сервер предназначен для локального выполнения ПР4. Авторизация и роли в этой работе не вводятся. Сервер по умолчанию слушает только `127.0.0.1`.

## Запуск

Из папки проекта в первом терминале:

```powershell
node api/mock-server.js --port 8080 --origin http://127.0.0.1:5555
```

Проверка: `http://localhost:8080/api/__health`. Во втором терминале:

```powershell
flutter run -d chrome --web-hostname=127.0.0.1 --web-port=5555 --dart-define=API_BASE_URL=http://localhost:8080/api
```

Открывать клиент нужно по адресу `http://127.0.0.1:5555`. Если используется `http://localhost:5555`, сервер запускается с `--origin http://localhost:5555`. Источник включает протокол, имя хоста и порт; `localhost` и `127.0.0.1` — разные источники.

Сервер создаёт `api/data/alibi.json` из `api/seed.json` при первом запуске. Изменения записываются на диск перед успешным ответом и сохраняются после перезапуска. Рабочая база исключена из Git. Повреждённая база не заменяется начальным набором автоматически. Старое хранилище ПР3 в браузере не удаляется; приложение ПР4 использует сервер. Пользовательские данные из localStorage автоматически не импортируются.

## Ресурсы и операции

Одинаковые операции доступны для `requests` (заявки), `clients` (клиенты с картой), `employees` (сотрудники), `services` (услуги), `scenarios` (сценарии).

| Метод и путь | Назначение | Успешный ответ |
| --- | --- | --- |
| `GET /api/__health` | Проверка сервера | `200`, состояние сервера |
| `GET /api/{resource}` | Поиск и страница каталога | `200`, оболочка списка |
| `GET /api/{resource}/options` | Полные варианты для связанных полей, включая корзину | `200`, массив записей |
| `GET /api/{resource}/{id}` | Карточка, в том числе запись в корзине | `200`, запись и `relations` |
| `POST /api/{resource}` | Создание; ID назначает сервер | `201`, созданная запись |
| `PUT /api/{resource}/{id}` | Изменение активной записи | `200`, изменённая запись |
| `DELETE /api/{resource}/{id}` | В корзину | `204`, без тела |
| `DELETE /api/{resource}/{id}?hard=true` | Окончательное удаление | `204`, без тела |
| `POST /api/{resource}/{id}/restore` | Восстановление | `200`, запись |
| `POST /api/{resource}/bulk-delete` | Массовое удаление | `200`, `{"deleted": 2}` |

Тело массового удаления: `{"ids": [25, 26], "hard": false}`. Сначала сервер проверяет все выбранные записи. При конфликте ни одна запись не удаляется. Наличие связанных заявок (включая корзину) запрещает оба вида удаления клиента, сотрудника, услуги или сценария; наличие сценариев дополнительно запрещает удаление услуги. Конфликт возвращается как `409` с количеством связей.

Варианты `/options` запрашиваются по необходимости при первом открытии формы и кэшируются. Изменение соответствующего справочника в текущем приложении сбрасывает его кэш. Основные каталоги используют постраничный эндпоинт. `relations` содержит связи текущей карточки, а не копию всех заявок.

## Параметры списка

| Параметр | Значение |
| --- | --- |
| `search` | Поиск без учёта регистра по имени/теме, номеру, почте, описанию, ID |
| `category` | Тип заявки / город клиента / специализация сотрудника / категория услуги / ID услуги сценария |
| `status` | Статус заявки |
| `dateFrom`, `dateTo` | Включительный диапазон дат `YYYY-MM-DD` |
| `sort` | `date,desc`, `name,asc`, `price,asc`, `urgency,desc`; направление `asc` или `desc` |
| `page` | Номер страницы начиная с 1 |
| `size` | Размер страницы: по умолчанию 10, максимум 100 |
| `includeDeleted` | `true` включает записи в корзине |
| `__delay` | Диагностическая задержка в миллисекундах, максимум 10000 |
| `__fail` | Диагностический ответ: 400, 401, 403, 404, 409, 422, 500 или 503 |

Пример:

```text
GET /api/requests?search=встреча&status=newRequest&sort=date,desc&page=2&size=10
```

Оболочка: `{"items": [...], "page": 2, "size": 10, "total": 24, "totalPages": 3, "filters": [{"value": "...", "label": "..."}]}`. Значения фильтра вычисляются сервером по всему каталогу и приходят вместе со страницей. При выходе за последнюю страницу сервер возвращает последнюю доступную. Для пустого результата `items: []`, `total: 0`, `page: 1`, `totalPages: 1`.

В URL клиента используются прежние параметры ПР3 (`deleted=1`, `category`, `sort`, `page`, `size`); репозиторий преобразует их в параметры API. `__delay` и `__fail` можно добавить прямо в адрес клиента, они будут переданы серверу.

## Форматы записи и чтения

На запись заявки отправляются `code`, `title`, `type`, `status`, `eventDate`, `urgency`, `clientId`, `serviceId`, `employeeIds`, `scenarioIds`. Сервер назначает `id`, `createdAt`, `deletedAt`. Статусы: `newRequest`, `inProgress`, `ready`, `closed`; типы: `lateForWork`, `missedMeeting`, `missedDeadline`, `awkwardEvent`.

В ответе заявки вместо ID связей приходят объекты `client`, `service` и массивы `employees`, `scenarios`. `AlibiRequest.fromJson` поддерживает и развёрнутые связи, и прежний формат с ID. У сценария на запись отправляется `serviceId`, а на чтение возвращается `service`.

Поля остальных сущностей сохраняют имена моделей ПР3:

| Сущность | Поля на запись |
| --- | --- |
| Клиент | `name`, `email`, `city`, `joinedAt`, `card: {number, issuedAt, points}` |
| Сотрудник | `name`, `email`, `phone`, `specialty`, `hiredAt`, `experienceYears` |
| Услуга | `name`, `description`, `category`, `price`, `createdAt` |
| Сценарий | `name`, `description`, `serviceId`, `durationMinutes`, `createdAt` |

Числа передаются числами JSON, списки ID — массивами чисел. Карта клиента вложена в клиента. Дополнительные поля клиента не считаются отдельным ресурсом.

## Ошибки

Формат обычной ошибки: `{"message": "Понятное описание"}`. Для `422` добавляется `errors`, например:

```json
{"message": "Ошибка валидации", "errors": {"code": "Такое значение уже используется"}}
```

Ключи совпадают с полями формы. Для вложенной карты используются `cardNumber`, `cardIssuedAt`, `cardPoints`. Уникальность номера заявки, почты внутри каталога и номера карты проверяется сервером с учётом корзины и исключением редактируемой записи. Сервер проверяет форматы, диапазоны, реальные даты, существование связей, принадлежность сценария услуге. При изменении услуги сценария проверяются уже связанные заявки.

| Ответ / сбой | Исключение приложения |
| --- | --- |
| 400 | `BadRequestException` |
| 401 | `UnauthorizedException` |
| 403 | `ForbiddenException` |
| 404 | `NotFoundException` |
| 409 | `ConflictException` |
| 422 | `ValidationException` с ошибками полей |
| 5xx / неверная структура JSON | `ServerException` |
| Сбой соединения / таймаут / блокировка CORS | `NetworkException` |
| Отмена устаревшего поиска | `RequestCancelledException` |

Интерсептор разбирает 4xx, `guard` преобразует остальные ошибки Dio. Виджеты не импортируют Dio. В debug-режиме журнал содержит метод, адрес и код ответа. Для чтения допускаются три попытки всего с паузами 350 и 700 мс только при сетевом сбое. HTTP-ошибки и отмена не повторяются; изменения данных не повторяются. При новом вводе поиска старый запрос отменяется, а отменённый ответ не меняет страницу.

## CORS и демонстрация

Сервер отвечает на `OPTIONS` кодом 204 и указывает разрешённый источник, методы и заголовки `Content-Type, Authorization`. Заголовки присутствуют и в ответах с ошибками.

Для воспроизведения CORS запустите сервер с неверным источником `--origin http://127.0.0.1:5556`, а клиент оставьте на 5555. Проверка `/__health` в отдельной вкладке может работать, но запрос из приложения блокируется браузером. В Console виден текст CORS, в Network — предварительный `OPTIONS`/неуспешный запрос. Исправление — перезапуск сервера с источником `http://127.0.0.1:5555` и повтор загрузки.

Проверки:

```powershell
flutter analyze
flutter test
node --test api/server.test.js
flutter build web --release --dart-define=API_BASE_URL=http://localhost:8080/api
```
